Architecture

How product identity resolution works over the TJX purchase-order data

The Problem

Product identity resolution over TJX purchase-order data: group the rows that refer to the same physical product. The extract holds roughly two million rows (1,999,911 exactly), and the same product recurs across purchase orders under slightly different vendor names, styles, and descriptions. The task is to decide which of those rows are the same thing.

TJX supplies its own product cluster IDs (PS_PRODUCT_ID), which serve as the ground truth the retrieval quality is measured against.

Pipeline and Technical Approach

A single Databricks Asset Bundle job, create_ai_search_index, runs three chained tasks. Each task is independently re-runnable, so a failure late in the chain does not force a re-read of the CSV or a re-embed of the two million rows.

TASK 1
ingest_raw
Reads the CSV from a Unity Catalog volume into the _bronze table verbatim, and asserts the row count is exactly 1,999,911.
→
TASK 2
build_search_table
Normalizes null sentinels, gates EXPORT_COUNTRY, derives embed_text, quarantines broken rows, and enables Change Data Feed.
→
TASK 3
create_index
Creates the Databricks Vector Search index with managed embeddings, or syncs it if it already exists.

The job produces these tables in ${catalog}.${schema}:

po_products_ai_search
The indexable table.
po_products_ai_search_bronze
The raw CSV as loaded.
po_products_ai_search_quarantine
The ~3,176 field-shifted rows.
po_products_ai_search_dedupe
The deduplicated, curated variant used for retrieval.

embed_text

Vector Search's managed embeddings read a STRING column, never a STRUCT. The columns listed in ai_search.embedding_cols are therefore flattened into a single string. No struct column is materialized, since those fields already exist as columns of their own.

Each value is prefixed with its lowercased column name, which gives the embedding model a field cue: vendor_style: 710849298007 reads differently than a bare digit string. The prefix is derived from the column name, so embedding_cols alone controls the output — no code edit is needed to change what gets embedded. 

vendor_name: RALPH LAUREN EUR/BLUE LABEL | vendor_style: 710849298007 |
product_description: 601 POPLIN SPORT SHIRT | department_description: BEST BRANDS | ...

Each column becomes a labelled fragment. The lowercased column name is the prefix; NULL fields drop out entirely rather than leaving an empty fragment behind:

vendor_name:RALPH LAUREN EUR/BLUE LABEL vendor_style:710849298007 product_description:601 POPLIN SPORT SHIRT department_description:BEST BRANDS export_country:NULL

The ai_search.embedding_cols entry in config.yaml is the single source of truth for what goes into this string — no code edit needed to change what gets embedded.

Data Defects Handled

All four were present in the data exactly as the customer sent it.

↔ Field shift
3,176 rows · 0.159%
An inch mark in a product name (12" CERAMIC WOK) was double-escaped at export, pushing every later value one column right. Detected via CONFIDENCE_SCORE being non-numeric; these rows are quarantined rather than indexed.
⏎ Embedded newlines
14 of 25 source parts
Quoted fields contain literal newlines and no row ends with a trailing newline. The reader requires multiLine=true and escape='"'; the row-count assertion in ingest_raw is the tripwire.
∅ Null sentinels
None / NA / -
Literal None, NA, and - strings mean "missing" but are not empty. Normalized to NULL before embedding, matching whole values only so a vendor named ST. JOHN survives untouched.
⚠ Structural nullity
EXPORT_COUNTRY · 64% missing
Missingness correlates with the import/domestic flag (0% missing on IMPORT rows). Left raw it would leak that flag into similarity, so it is NULLed on non-IMPORT rows.

Evaluation Criteria

The headline metric is precision@k: of the products the index returns, how many share the input row's PS_PRODUCT_ID. Recall@k — whether any sibling came back at all — is reported alongside, but it answers a narrower question than a practitioner scanning a result list actually cares about.

What the Evaluate button does

Evaluate answers one question the search box cannot: across many products at once, does the index actually return same-product rows? Every step is scored against TJX's own PS_PRODUCT_ID clusters, so the ground truth is the customer's, not ours. Clicking it runs this loop server-side (queries run in parallel, so a hundred samples finish in seconds rather than minutes):

STEP 1 · SAMPLE
Draw n eligible rows
Randomly sample n rows (the "Eval N" input) from the chosen variant's table. Only eligible clusters are drawn: a cluster must hold more than one distinct embed_text, so there is a real sibling to find — not just a byte-identical copy of the query. "Multi-VSN only" further restricts to clusters spanning more than one vendor style, the population semantic search actually has to earn.
→
STEP 2 · QUERY
Ask the index with each row's own text
For every sampled row, query the index with that row's embed_text (HYBRID or ANN, as toggled), fetching k + 50 results. The over-fetch lets exact-duplicate texts be dropped without starving the top-k window.
→
STEP 3 · SCORE
Count same-cluster hits in the top k
Discard results whose text is identical to the query, keep the top k of what remains, and count how many share the query's PS_PRODUCT_ID. precision = matched ÷ min(k, siblings); the query counts as a recall hit if it found any sibling. It also checks the query retrieves itself — if not, the index is stale.
→
STEP 4 · AGGREGATE
Average across the sample
Mean the per-query scores into the numbers shown in Evaluation Results: Precision@k, Recall@k, Found something (queries with at least one hit), Correct / Possible, and Capped by ground truth.
Why query a row against an index that already contains it? The query's own text is excluded from scoring — a cluster with t distinct texts offers t−1 findable siblings — so the test is whether the index bridges a genuine textual difference to a same-product row, not whether it can echo the query back.

Why the denominator is min(k, siblings), not k

The precision denominator is min(k, siblings_available), not k. Most clusters simply do not contain enough distinct products to fill ten result slots, so dividing by a fixed k=10 would penalize a system that already returned every sibling that exists:

49.9%
of clusters hold exactly one distinct product
2
median distinct products per cluster
12.8%
of clusters contain enough products to fill 10 slots
Dividing by a fixed k=10 would score a system that returned every sibling that exists at only 0.2. For the same reason, k defaults to 3. slots_capped_by_ground_truth reports how often that ceiling binds.

Recall is measured against TJX's own cluster IDs, and self_not_returned should be near zero — if a row cannot retrieve itself, the index is stale or the sync is incomplete.
